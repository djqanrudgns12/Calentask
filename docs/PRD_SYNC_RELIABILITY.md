# PRD — 동기화 신뢰성 확보 (Calentask ↔ Google ↔ Naver)

> 작성일: 2026-08-25
> 선행 문서: `docs/SYNC_ARCHITECTURE.md`
> 상태: **P0 구현 완료 (배포 전 마이그레이션 1건 필요)**

## ⚠️ 배포 전 필수 작업

`supabase/migrations/20260826010000_allow_force_sync_mode.sql` 를 **먼저 적용**해야 합니다.
`google_sync_jobs.mode`에 `CHECK (mode IN ('FULL','RETRY'))` 제약이 걸려 있어,
적용하지 않으면 "다시 보내기" 버튼이 DB에서 거부되어 **아무 일도 일어나지 않습니다.**

Supabase 대시보드 → SQL Editor에 파일 내용을 붙여넣고 실행하시면 됩니다.

## 1. 문제 정의 (사용자가 겪은 것)

- Calentask에 일정을 등록하면 **구글 캘린더에는 들어간다.**
- 그런데 **일부 일정만 네이버 캘린더에 나타나지 않는다.**
  - 반영됨: `한려 송별회(남자)` (8/26)
  - 반영 안 됨: `한려 환영 회식` (9/1), `체육과 정기연수` (9/11)
- "지금 동기화"를 아무리 눌러도 상태가 바뀌지 않는다. **약 10회 시도, 매번 실패.**

---

## 2. 조사 방법 (추측이 아니라 실측)

Supabase 운영 DB를 **읽기 전용**으로 조회해 다음을 확인했습니다.

- `users.google_sync_settings` (라우팅 매핑 실제 값)
- 문제 일정 3건의 `activities` 행 전체 (구글 링크 · 해시 · 시각)
- `sync_history` 325건 전수 (시간순 이력)
- `google_sync_jobs` 최근 4건 (`failed_items` 포함)
- 제목+시작시각 기준 중복 활동 전수

## 3. 실측 결과 — 결정적 증거

### 3.1 세 일정은 **같은 캘린더 문제가 아니다**

| 일정 | 카테고리 | 구글 캘린더 | 구글 반영 시각(UTC) | 네이버 |
|---|---|---|---|---|
| 한려 송별회(남자) | 개인 | **개인** | 07:52:33 | ✅ |
| 한려 환영 회식 | 개인 | **개인** | 07:54:49 | ❌ |
| 체육과 정기연수 | 출장 | 복무 | 07:55:22 | ❌ |

앞의 두 건은 **완전히 같은 구글 캘린더(`개인`)** 에 있습니다.
→ "네이버가 그 캘린더를 구독 안 해서"가 **아닙니다.** 차이는 **구글에 기록된 시각 2분**뿐입니다.

### 3.2 오늘 아침 구글 캘린더에 일어난 일

`sync_history` 전수 조회 결과:

```
07:23:50  DELETED  ALL   중복 이벤트 정리 (150건 제거)      ← 구글 이벤트 150개 삭제
07:23:53  BATCH    FAILED  4건 반영, 1건 실패
07:25:02  BATCH    FAILED  0건 반영, 3건 건너뜀, 1건 실패    ← 삭제분이 복구되지 않음
   …………  약 29분간 구글 캘린더에 일정 150건이 존재하지 않는 "공백 구간" …………
07:52:28  DELETED  ALL   구글 연결 정리 (중복 0건 제거, 링크 150건 복구)
07:52:37~ BATCH    SUCCESS 151건 재전송                     ← 이때 전부 다시 생성됨
07:56:54  JOB      SUCCEEDED  synced 0 / skipped 153 / failed 1  ← 사용자의 마지막 시도
```

**해석**
1. 07:23에 우리 코드가 **구글 이벤트 150건을 지웠습니다.**
2. 07:52까지 **약 29분 동안 구글 캘린더가 비어 있었습니다.**
3. 네이버는 이 공백 구간 어딘가에서 자기 주기로 구글을 읽어 갔고, **없는 것을 없는 대로 반영**했습니다.
4. 07:52에 151건이 다시 만들어졌습니다. `한려 송별회`(07:52:33)는 이 물결에 올라타 네이버로 전달됐습니다.
5. `한려 환영 회식`(07:54:49)과 `체육과 정기연수`(07:55:22)는 **네이버가 그 직전에 읽고 지나간 뒤에** 만들어졌습니다.
6. 그리고 07:56에 사용자가 누른 동기화는 **`synced 0 / skipped 153`** — 아무것도 전송하지 않았습니다.
   구글의 `updated` 값이 그대로이므로 **네이버가 다시 가져갈 이유가 영영 생기지 않습니다.**

> **이것이 "10번을 눌러도 안 고쳐진" 정확한 이유입니다.**
> 버튼은 정상 동작했습니다. 다만 **보낼 게 없다고 판단하고 아무것도 안 보낸 것**입니다.

### 3.3 모든 배치가 실패로 끝나던 이유

`google_sync_jobs.failed_items` — 최근 4개 작업 **전부 동일**:

```json
{ "id": "b11930dd-…", "title": "Happy birthday!", "error": "Event type cannot be changed." }
```

구글이 자동 생성한 **생일 일정**(연락처 기반, `eventType: "birthday"`)이
사용자의 기본 캘린더(primary)에서 Calentask로 **수입**되었고,
Calentask가 그것을 **일반 일정으로 되밀려다** 구글에게 영구 거부당하고 있습니다.
이 1건 때문에 모든 배치 작업이 `FAILED`로 표시되고, 사용자는 실패를 보고 또 재실행 → **churn 가속**.

### 3.4 라우팅이 실제로 튄 흔적

```
03:19:31  UPDATED  Calentask(기본)  한려 환영 회식     ← 개인 캘린더에 있어야 할 일정이 기본 캘린더로 이동
03:21:19  DELETED  Calentask(기본)
03:21:09  CREATED  개인             한려 송별회(남자)
03:21:54  DELETED  Calentask(기본)
```

같은 일정이 `개인` → `Calentask(기본)` → 삭제 → `개인` 으로 오갔습니다.
구글 안에서는 `events.move`라 안전하지만, **네이버 입장에서는 "삭제 후 재생성"의 반복**입니다.

## 4. 근본 원인 (Root Cause)

### RC-1. 외부 미러를 고려하지 않은 "구글 이벤트 대량 삭제 → 재생성" (churn)

`reconcileGoogleDuplicates()`가 **상한 없이** 구글 이벤트를 삭제합니다.
삭제와 재생성 사이에 시간 간격이 생기면, 그 사이에 폴링한 미러(네이버)는 **비어 있는 상태를 정답으로 복제**합니다.
우리는 그 사실을 알 수도, 되돌릴 수도 없습니다.

> **원칙 위반**: 다운스트림 미러가 존재하는 시스템에서 "지웠다가 다시 만든다"는 절대 금지 패턴입니다.
> 항상 **제자리 갱신(update-in-place)** 이어야 합니다.

### RC-2. 해시 스킵 함정 (skip trap) — **가장 악질적인 원인**

`google_content_hash`가 같으면 구글 왕복을 건너뜁니다.
문제는 **"구글에는 맞게 들어 있지만 네이버에는 없다"는 상태를 우리 시스템이 표현할 방법이 없다**는 것입니다.

- 우리 DB: "보낼 것 없음" ✅
- 구글: "정상" ✅
- 네이버: "없음" ❌ ← **아무도 이 상태를 모름**

그리고 사용자에게는 **강제로 다시 보낼 수단이 전혀 없습니다.**
단건 `forceSyncActivityAction`은 해시를 무시하지만, **UI에서 전체에 적용할 방법이 없습니다.**

### RC-3. "빈 카테고리 = 기본 캘린더" 라우팅 규칙

```ts
desiredCalendarFor(categories, settings, scope)
  = mappedCalendarFor(categories, settings) || scope.writeCalendarId
```

`categories`가 비면 **무조건 기본 캘린더(Calentask)** 로 목적지가 잡히고,
이미 다른 캘린더에 있던 이벤트가 `events.move`로 **끌려갑니다.**

그런데 `updateActivity(id, payload, categoryIds)`는 **부분 수정에서도 카테고리 전체를 요구**합니다.

```ts
// src/app/actions/calendar.ts — updateActivity
await supabase.from('activity_category_map').delete().eq('activity_id', id)   // 무조건 전부 삭제
if (categoryIds.length > 0) { /* 다시 삽입 */ }                                // 비면 그대로 소멸
```

→ 시각만 바꾸는 경로(달력 드래그 이동 등)에서 호출자가 카테고리 배열을 정확히 재전송하지 못하면
   **(a) 일정의 카테고리가 통째로 사라지고 (b) 구글 이벤트가 기본 캘린더로 이동**합니다.
   `useEventDragDrop.ts:77`의 `draggedEvent.categories?.map(...) || []` 는 캐시에 `categories`가
   없을 때 조용히 `[]`가 되는 구조입니다.

**설계 결함: "지정 안 함(undefined)"과 "전부 해제(빈 배열)"를 구분하지 않습니다.**

### RC-4. 구글 시스템 이벤트를 필터링하지 않음

`applyDelta()`는 `event.eventType`을 보지 않습니다.
구글의 `birthday` / `fromGmail` / `workingLocation` / `focusTime` / `outOfOffice` 이벤트는
**읽기만 가능하고 일반 일정으로 수정할 수 없습니다.**
이것들이 수입되면 이후 모든 push가 영구 실패합니다.

### RC-5. 다중 카테고리 라우팅이 비결정적

```ts
for (const cat of categories) { const mapped = settings.groupMapping[cat?.id]; if (mapped) return mapped }
```

`categories` 배열 순서는 Supabase 조인 결과에 따라 달라질 수 있습니다.
카테고리 2개가 서로 다른 캘린더로 매핑되어 있으면, **실행할 때마다 목적지가 바뀌어
이벤트가 두 캘린더 사이를 왕복**합니다. 네이버에는 삭제/생성이 반복됩니다.

### RC-6. 네이버는 코드에 없다 — 기대와 현실의 간극

사용자의 기대는 "3자 양방향"이지만, 현재 구조는 **2자 양방향 + 1자 단방향 미러**입니다.
- 네이버에서 수정/추가한 것은 **구글로도 Calentask로도 오지 않습니다.**
- 네이버에 "지금 다시 가져가라"고 요청할 수단이 없습니다.

## 5. 목표 (Goals)

| # | 목표 | 성공 기준 |
|---|---|---|
| G1 | 구글 이벤트를 **지웠다 다시 만들지 않는다** | 자동 경로에서 `events.delete` 호출 0건 (사용자가 일정을 실제로 지운 경우 제외) |
| G2 | 사용자가 **외부 미러 재동기화를 강제**할 수 있다 | 버튼 1회로 전체 이벤트의 구글 `updated`가 갱신됨 |
| G3 | 라우팅이 **결정적**이고, 의도치 않게 바뀌지 않는다 | 같은 입력 → 항상 같은 목적지. 시각만 수정하면 캘린더가 바뀌지 않음 |
| G4 | 구글 시스템 이벤트가 **동기화를 오염시키지 않는다** | `google_sync_jobs.failed` = 0 |
| G5 | 사용자가 **현재 상태를 눈으로 확인**할 수 있다 | 일정별 "어느 구글 캘린더에 있는지 / 마지막 전송 시각" 표시 |
| G6 | 네이버의 한계를 **정직하게 안내**한다 | 설정 화면에 단방향·주기 지연 명시 + 체크리스트 제공 |

### Non-Goals (이번 범위 아님)

- 네이버 캘린더 **직접** 연동(네이버 OpenAPI/CalDAV) — 별도 검증 과제(9절)
- 동기화 엔진 재작성 — 기존 안전장치(구조 문서 8절)는 그대로 유지

## 6. 요구사항 (Requirements)

### P0 — 지금 당장 (오늘 배포 목표)

#### R1. 미러 세이프 재전송 (Force Re-emit) — **G2**

> **왜**: 네이버가 놓친 일정을 되돌릴 유일한 방법은, 구글 이벤트의 `updated`를 강제로 갱신하는 것입니다.

- `google_sync_jobs`에 `mode: 'FORCE'` 추가.
- `syncBatchActivitiesToGoogle(userId, activities, onProgress, { force: true })`
  → **해시 스킵을 무시하고 전부 `events.update` 수행** (내용은 동일, `updated`만 갱신).
- `events.delete` / `events.insert`는 절대 하지 않음 → 미러가 잃어버릴 위험 0.
- UI: 고급 설정 → "외부 캘린더(네이버 등) 다시 보내기" 버튼 + 설명 문구.

**수용 기준**
- 버튼 실행 후 `synced == 대상 건수`, `skipped == 0`.
- 실행 중 구글 캘린더에서 일정이 한 순간도 사라지지 않음.

#### R2. 중복 정리 안전 브레이크 — **G1**

- `reconcileGoogleDuplicates()`에 삭제 상한 도입 (`RECONCILE_DELETE_LIMIT = 20`).
- 상한 초과 시: **삭제하지 않고** 링크 복구만 수행 + `sync_history`에 경고 기록.
- 자동 실행(`runExportJob`의 FULL 시작 시)에서는 **삭제를 아예 하지 않음**(링크 복구만).
  삭제는 사용자가 "중복 정리"를 명시적으로 눌렀을 때만.

**수용 기준**: 배치 동기화만으로는 구글 이벤트가 하나도 삭제되지 않는다.

#### R3. 구글 시스템 이벤트 차단 — **G4**

- `applyDelta()`: `event.eventType`이 `default`가 아니면 **수입하지 않음**
  (`birthday`, `fromGmail`, `workingLocation`, `focusTime`, `outOfOffice`).
- `placeEvent()`: `Event type cannot be changed` 류의 영구 오류는 **실패가 아니라 "건너뜀(읽기 전용 일정)"** 으로 처리.
- 기존에 수입된 오염 행(`b11930dd` 등)은 구글 링크를 끊어 재시도 대상에서 제외.

**수용 기준**: 배치 작업의 `failed`가 0, 상태가 `SUCCEEDED`로 표시됨.

#### R4. 라우팅 결정성 + 의도치 않은 이동 차단 — **G3**

- **R4-a. `categoryIds` 선택적화**
  `updateActivity(id, payload, categoryIds?: string[])`
  - `undefined` → 카테고리 매핑을 **건드리지 않음**, 구글 push 시 **DB에서 현재 카테고리를 다시 읽어** 사용.
  - `[]` → "전부 해제" 의도로만 동작.
  - 시각만 바꾸는 호출부(`useEventDragDrop`, `moveCalendarEvent`)는 인자를 **생략**하도록 수정.

- **R4-b. 근거 없으면 옮기지 않는다**
  `desiredCalendarFor()`: 카테고리가 비어 있고 이미 우리 캘린더에 연결돼 있으면
  **현재 위치를 유지**(기본 캘린더로 끌어오지 않음).

- **R4-c. 결정적 우선순위**
  `mappedCalendarFor()`: 후보를 `category.id` 오름차순으로 **정렬한 뒤** 첫 매핑 채택.
  (추후 사용자 지정 우선순위로 확장)

- **R4-d. 캘린더 이동 로그**
  `events.move` 실행 시 `sync_history`에 `MOVED` 액션으로 출발지/목적지 기록.

**수용 기준**
- 달력에서 일정을 드래그해 옮겨도 카테고리가 유지되고 구글 캘린더가 바뀌지 않는다.
- 같은 일정을 10회 동기화해도 목적지 캘린더가 항상 동일하다.

### P1 — 이번 주

#### R5. 동기화 상태 진단 화면 — **G5**

일정별로 다음을 표시: 구글 캘린더 이름 / 이벤트 ID / 마지막 전송 시각 / 마지막 결과.
"이 일정만 다시 보내기" 버튼(기존 `forceSyncActivityAction` 재사용).

#### R6. 네이버 안내 강화 — **G6**

고급 설정에 고정 안내 블록:
- 네이버 연동은 **구글 → 네이버 단방향**이며 즉시 반영이 아님
- **새로 만든 구글 캘린더는 네이버에서 다시 선택**해야 보임 (그룹 6개 전부 체크 필요)
- 안 보일 때 순서: ① 네이버에서 해당 캘린더 구독 확인 → ② "다시 보내기"(R1) → ③ 10~30분 대기

#### R7. 라우팅 미리보기

고급 설정에서 매핑을 바꿀 때 **"이 변경으로 N건이 A→B로 이동합니다"** 를 먼저 보여주고,
"이동" / "새 일정부터 적용" 중 선택하게 함. (현재 `migrationPrompt`를 확장)

### P2 — 검증 후 결정

#### R8. 네이버 직접 연동 타당성 검증

- 네이버 캘린더 OpenAPI(`openapi.naver.com/calendar/createSchedule.json`)의
  **현재 제공 여부 / 생성 외 수정·삭제·조회 가능 여부 / CalDAV 지원 여부**를 실측 확인.
- 가능하다면 `NaverCalendarAdapter`를 별도 모듈로 추가해 진짜 양방향 구현.
- 불가능하면 **"네이버는 보기 전용 미러"** 를 제품 사양으로 명확히 고정.

## 7. 설계 원칙 (앞으로 이 코드를 고칠 때의 규칙)

1. **자동 경로에서 구글 이벤트를 삭제하지 않는다.** 사용자가 일정을 지웠을 때만 삭제한다.
2. **최적화(스킵)에는 반드시 탈출구를 둔다.** 건너뛸 수 있으면, 강제로 보낼 수단도 있어야 한다.
3. **"모른다"와 "없다"를 구분한다.** `undefined`(미지정)와 `[]`(비었음)는 다른 의미다.
4. **라우팅은 결정적이어야 한다.** 같은 입력이면 언제나 같은 목적지.
5. **외부 미러는 우리의 중간 상태를 본다.** 중간 상태가 "비어 있음"이면 안 된다.
6. **실패를 실패로 표시하되, 영구 실패는 재시도 대상에서 뺀다.**

### 알려진 트레이드오프

자동 경로가 더 이상 구글 이벤트를 지우지 않으므로, **중복 사본이 생기면 스스로 사라지지 않습니다.**
이것은 의도적입니다 — 남은 중복은 눈에 거슬릴 뿐이지만, 잘못된 삭제는 네이버에서 **일정을 잃는 일**이기 때문입니다.
정리가 필요하면 위험 구역의 "중복 사본 정리하기"를 사용합니다.
(현재 사용자 DB 기준 중복 사본은 0건이므로 당장 문제되지 않습니다.)

## 11. 배포 후 실행 순서 (사용자가 할 일)

1. **마이그레이션 적용** — Supabase 대시보드 → SQL Editor에
   `supabase/migrations/20260826010000_allow_force_sync_mode.sql` 내용을 붙여넣고 실행.
   (이걸 건너뛰면 "다시 보내기" 버튼이 동작하지 않습니다.)
2. **배포** — 변경된 코드를 Vercel에 배포합니다.
3. **네이버 캘린더 구독 목록 확인** — 네이버 캘린더 → 설정 → 외부 캘린더/구글 연동에서
   `업무·복무·개인·동아리·Calentask·학사일정` **6개가 모두 체크**되어 있는지 확인합니다.
   Calentask가 만든 구글 캘린더는 **네이버에 자동으로 추가되지 않습니다.**
   이 단계에서 빠진 캘린더가 있으면 그 그룹의 일정은 애초에 네이버로 갈 수 없습니다.
4. **Calentask → 고급 설정 → 그룹 및 라우팅 → "전체 일정 다시 보내기"** 실행.
   진행 창에서 `건너뜀 0건`, `실패 0건`으로 끝나는지 확인합니다.
5. **10~30분 대기 후 네이버 확인** — `한려 환영 회식`, `체육과 정기연수`가 보이는지 봅니다.

4번에서 `실패`가 있었는지, 3번에서 해당 캘린더가 빠져 있었는지를 먼저 확인해 주세요.
